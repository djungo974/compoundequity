## Normalizer / dedupe (Phase 5, step 2 — done)

All three collectors now remember what they've already sent, so a run with nothing new posts "No new items since last run" instead of repeating yesterday's digest.

- **Storage**: one shared n8n Data Table, `radar_seen_items` (id `pxh42kN8hGM9MiRb` — recreated once, from `loPeSajCWOCZg9ed`, to add the `score`/`reason` columns below; the n8n API doesn't support altering an existing table's columns in this version), columns `sector` / `link` / `title` / `first_seen_at` / `score` / `reason`. All three sectors write to the same table, distinguished by the `sector` column (`uranium` / `mining` / `defense`).
- **Mechanism**: rather than n8n's native Data Table node (its exact parameter schema wasn't documented enough to wire blind), each collector calls the Data Table's own REST API from inside the workflow — an HTTP Request node (`Get Seen Links`) reads existing rows, a Code node (`Filter New Items`) drops anything already seen, and a second HTTP Request node (`Insert Seen Rows`) records the survivors after they're sent. Auth is a dedicated credential, `RADAR - n8n API Key` (httpHeaderAuth, header `X-N8N-API-KEY`), so the workflow authenticates to n8n's own API the same way I do from outside.
- **What actually broke, twice, before this worked**: (1) the Code node threw `Cannot assign to read only property` when referencing the seen-links node by name (`$('Get Seen Links')`) instead of by a direct graph connection — fixed by wiring it through an explicit `Merge with Seen` node instead of a cross-reference; (2) `Get Seen Links` then failed with a genuine `400 Bad Request` — the Data Table rows API caps `limit` at 250, and the URL asked for 500. Neither was the "VPS can't call its own hostname" theory I suspected partway through — that was a red herring from testing a stale, unsaved copy of the workflow still open in the browser.

## 1–5 importance scorer (Phase 5, step 3 — done)

Each collector now scores its up-to-15 new items with DeepSeek before sending, using the rubric from `docs/editorial-format.md`.

- **Model**: DeepSeek (`deepseek-chat`), called directly via its OpenAI-compatible REST API (`https://api.deepseek.com/v1/chat/completions`) from a plain HTTP Request node — not n8n's dedicated LangChain/Anthropic node, whose exact parameter schema wasn't reliably documented. Authenticated with your existing `DeepSeek account` credential via n8n's "Predefined Credential Type" HTTP Request option, so no new key was created.
- **Why DeepSeek and not Claude**: your `Anthropic account` credential's balance was too low (`400` from the API, "credit balance is too low") the moment this was tried. Switched to DeepSeek on your instruction rather than topping up Anthropic. The Anthropic version of these nodes worked correctly right up to that billing wall, so switching back later is a small edit (URL, credential, response field) if you prefer Claude once it's funded.
- **Flow**: `Limit 15` → `Prepare Scoring Request` (batches all 15 into one prompt, one API call per run rather than 15) → `Score Items (DeepSeek)` → `Merge Score Results` (rejoins the API response with the original items — the model's response doesn't carry the input fields, so a `Merge` node built the same way as the dedupe step's `Merge with Seen` reunites them) → `Parse Scores` (parses the model's JSON array, matches scores back to items by link, sorts highest-importance first) → digest and seen-table insert as before.
- **Digest format now includes the score and a one-line reason** per item, e.g. `- [4/5] Headline\n  Why it matters, per DeepSeek\nhttps://...`.

## Orchestrator (Phase 5, step 5 — done, and now live)

## Compliance checker (Phase 5, step 6 — done, basic)

Inserted into the Drafter between `Format Issue` and the Telegram send: a `Compliance Check` Code node scans the assembled issue text for a curated list of banned phrases (book a call, portfolio review, investor profile, target price, guaranteed return, tax/estate advice, "how much capital", "you should buy/sell", buy/sell signal, act now, don't miss), and confirms a Disclosure section and at least one source link are present. An `IF Compliance Pass` node routes PASS to the normal Telegram send, and FAIL to a separate `Send Compliance Alert` message listing the exact reasons instead of sending the (possibly bad) issue — nothing reaches the "final" Telegram slot unreviewed on a fail.

**Deliberately not attempted**: a blanket ban on the bare words "buy"/"sell" — real headlines legitimately contain them ("Cameco becomes exclusive buyer..."), and the brief's actual rule is about not directing the *reader* to buy or sell, not about avoiding the words in factual reporting. A regex can't reliably tell those apart, so the checker targets specific directive phrases instead. Also not attempted: dead-link checking (would need a live HTTP call per link) and unsourced-number detection (needs real NLP, not a keyword scan) — both remain manual-review items for now.

Also removed while touching all five Telegram-sending nodes: the default "This message was sent automatically with n8n" footer (`additionalFields.appendAttribution: false`), across all three collectors' digests and both of the Drafter's messages.

## Telegram approval step (Phase 5, step 7 — done, simplified)

On compliance PASS, the Drafter no longer sends a plain message — it sends the issue with three inline buttons (✅ Approve / ✏️ Edit / ❌ Reject), built and sent by calling Telegram's Bot API directly (`sendMessage` with a `reply_markup.inline_keyboard`) rather than through n8n's built-in Telegram "Send and Wait for Response" operation. That operation was deliberately avoided: its exact parameter schema (`approvalOptions`, `responseType`, wait-time limits) isn't reliably documented for this n8n version, and several open n8n GitHub issues describe it misbehaving on Slack/Teams/Telegram (auto-approving with no click, or looping). A second workflow, `RADAR – Approval Receiver` (`TTDuCya70cBfLjE0`), listens for button taps via its own Telegram Trigger (`updates: callback_query`) and logs each decision — `issue_id`, `action`, timestamp, and who clicked — to a new Data Table, `radar_approvals` (id `EGX0nj9rxU2rs7HZ`), then sends a short confirmation back to the chat. Tested with all three buttons; all three logged correctly.

**Reframed from the original brief, and flagged as a deliberate simplification**: your brief describes this step as gating an actual *send* — "auto-send on PASS + no reply by send time." There is nothing to gate yet, because no publish action exists (no Ghost integration). The Telegram message you see today already *is* the delivery — there's no separate subscriber-facing send happening after it. So right now, Approve/Edit/Reject only **records your decision** for track-record purposes; it doesn't hold anything back or release anything. There's also no timeout/auto-approve-if-no-reply logic — nothing is waiting on your answer. Once Ghost is wired up and an issue's "Approve" decision is what actually triggers a real publish, this will need the wait/timeout behavior added back in (at that point probably worth revisiting the native n8n Wait node's webhook-resume mode, using `radar_approvals` as the last known state if the timeout fires).

## Real bug found and fixed: empty-day runs broke the Orchestrator chain (Phase 5, step 10)

Testing the Orchestrator on a day with no fresh signals in one sector (mining, second run of the day) surfaced a genuine design flaw: when `Filter New Items` found zero new items, it returned zero output items — and in n8n, a node that receives zero input items simply doesn't execute. That zero-item gap propagated through the *entire* rest of that collector's chain (`Limit 15` → scoring → `Insert Seen Rows` → `Build Digest` → `Send to Telegram`), so **the collector produced no output at all**, not even its intended "No new items since last run" message. Because the Orchestrator's `Execute Workflow` nodes only pass control to the next step when the previous one returns at least one item, the whole pipeline silently stopped after whichever collector hit this — the run still showed `"status": "success"` in the API, which is why it wasn't obvious from execution status alone; it only showed up as "stops after Mining Collector" in the UI and by checking each sub-workflow's own execution history for `lastNodeExecuted`.

**Fix, applied to all three collectors identically**: `Filter New Items` now always returns exactly one item, tagged `status: 'HASITEMS'` or `status: 'EMPTY'`. A new `IF Has New Items` node branches immediately after it — the true branch is the existing scoring/digest/insert chain unchanged; the false branch goes straight to a new `Build Empty Digest` node (a one-line "No new items since last run" message) directly into `Send to Telegram`, skipping scoring and the seen-table insert entirely. This guarantees every collector always emits at least one Telegram-send output, so `Execute Workflow` always has something to hand to the next node in the Orchestrator. Confirmed by running the Orchestrator end to end with a genuinely empty sector in the middle of the chain — all four steps completed and a real Daily Radar issue was posted.

The Drafter got an analogous fix: if `Pick Lead Signals` finds no leads for any sector, `Format Issue` now returns a short "No new signals across any sector today" message instead of an almost-empty issue, and `Compliance Check` recognizes that exact message and passes it automatically (it would otherwise fail the "no source links" rule).

## Calendar source (Phase 5, step 11 — done)

The Drafter's section 4 ("On the calendar") is no longer a placeholder. A new `Get Calendar Events` HTTP node (parallel to `Get Today's Signals`/`Get ETF Holdings`) queries the same Federal Register API already used by the three collectors, filtered to the three agencies (`nuclear-regulatory-commission`, `energy-department`, `defense-department` — note these DOE/DoD slugs differ from the intuitive `department-of-energy`/`department-of-defense`, confirmed against the Mining/Defense collectors' own NRC-pattern nodes and verified live before deploying), requesting `effective_on` and `comments_close_on` alongside the usual title/link/date fields.

`Parse Calendar Events` (new Code node) keeps only documents whose effective date or comment deadline falls within the next 30 days, sorts soonest-first, dedupes by link+label, and caps at 5. `Merge Holdings with Draft` was expanded from 2 to 3 inputs to fold this branch in, and `Format Issue` renders each hit as `<date> — <label>: <title>` with a link, or "No confirmed regulatory dates (NRC/DOE/DoD) in the next 30 days" when none exist — never a fabricated or forecast date, per the editorial-format.md rule.

**Scope note**: this covers regulatory milestones only (rule effective dates, public-comment deadlines), not company earnings dates — no reliable free/automatable earnings-calendar source was found, unlike the worked example in `sample-brief.html` which cited a manually-sourced earnings date. Real-world Federal Register output also skews toward routine administrative notices (OMB comment-period boilerplate) as often as substantive rulemakings — the filter takes what's genuinely confirmed and sourced rather than curating for newsworthiness, matching the "never a forecast dressed up as a date" rule but meaning some issues' calendar section may be mundane on quiet weeks.

**Engineering note**: an early attempt to push this change to n8n was corrupted by a PowerShell/Windows encoding bug — `Get-Content -Raw | ConvertFrom-Json` without an explicit `-Encoding` reads UTF-8 files (like ones fetched by `curl`, which have no BOM) using the system ANSI codepage on Windows PowerShell 5.1, silently mangling every em-dash and emoji into mojibake before it was even sent. A first push briefly corrupted the live workflow's em-dashes/Telegram button emoji. Fixed by always using `[System.IO.File]::ReadAllText($path, [System.Text.Encoding]::UTF8)` / `WriteAllText(..., UTF8Encoding($false))` for any n8n JSON round-trip in PowerShell from here on, and by patching the existing `Format Issue` code surgically (string `.Replace()` on known substrings) rather than retyping it, so already-correct em-dashes already in production were never re-typed through PowerShell's default encoding path. Also hit and fixed along the way: the n8n PUT `/api/v1/workflows/{id}` schema rejects a `settings.binaryMode` field ("must NOT have additional properties") that GET happily returns — strip it before sending back.

## De-duplication in Holdings Refresh (Phase 5, step 12 — done)

Checked first whether the n8n Data Tables REST API had grown row-level `DELETE`/`PATCH`/upsert support since the earlier research (confirmed working now: whole-table `DELETE`/`POST /data-tables` both work) — but row-level delete is still not exposed (`DELETE /data-tables/{id}/rows/{rowId}` returns `404 not found` even for a row ID that genuinely exists), so wholesale delete+recreate-per-run was ruled out: it would change the table's ID every run, which the Drafter's `Get ETF Holdings` node references by a hardcoded URL — recreating monthly would mean also patching the Drafter (and anything else pointing at that ID) every run, adding real risk for a feature already flagged low-priority.

Went with a smaller, lower-risk fix instead: two new nodes, `Get Existing Holdings` (fetches the current table) and `Filter Changed Holdings` (a Code node, reaching back to `Merge All Holdings`'s output via `$('Merge All Holdings').all()`), sit between the existing parse branches and `Insert Holding Row`. A freshly-scraped row is only kept for insertion if it's new for that `etf`+`company`, or its `weight_pct` differs from the latest existing row by more than 0.01 — an unchanged holding no longer produces a duplicate row every month. `Insert Holding Row` itself needed no change since it already inserts per-item. Table ID (`SsRPwZKJNWSdX6hz`) and the Drafter's read path are both untouched, so this carries no cross-workflow risk.

Also found while in there: the `Monthly Schedule (1st, 06:00)` trigger documented in step 8 as added was **not actually present** in the live workflow (`triggerCount: 1`, i.e. Manual Trigger only) — re-added now, confirmed live.
